# Verify a Laravel upgrade

Request: `$ARGUMENTS`. Default to **evidence review only** unless runtime execution is explicitly requested and isolation is verified. A verification request does not authorize production access, migrations, queue consumption, cache deletion, deployment or source edits.

1. Read [shared rules](../laravel-upgrade/SKILL.md), the full [verification levels and gate catalog](../laravel-upgrade/references/verification.md), [templates](../laravel-upgrade/references/templates.md), [operations/rollback](../laravel-upgrade/references/operations.md), and the official guide for the hop. Confirm B=immutable original reference, P=previous completed hop and C=current candidate with matching source/manifest/lock/vendor/runtime per tree.
2. Inventory evidence validity: commits, lock/config hashes, PHP/extensions, deployment artifact, fixture revision, clock/timezone/locale, renderer versions and gate definitions. B=P only on the first hop. Reuse evidence only when every relevant input is unchanged and it belongs to the current closing round; a stale summary is not a test run.
3. Build the gate list from the tiers: Level 0 on every hop; Level 1 for features marked critical in the audit; Level 2 when risk/owner requires it. Record each PASS, FAIL, BLOCKED, NOT RUN or N/A with a concrete reason. Missing tools/fixtures are BLOCKED, never N/A. Only a specifically named, pre-approved Level 1/2 exception may continue as PARTIAL; a missing Level 0 never auto-advances.
4. Before executing approved gates, inspect tests/bootstrap/config for real service endpoints and destructive setup; provision disposable/synthetic local services and outbound controls. Ensure no cached production config, shared DB/cache prefix, live bucket, real mail/webhook or unreviewed GET side effect. If not safe, stop execution and report BLOCKED. For a request-forgery middleware-changing hop, include the mandatory real-CSRF check outside test-mode bypass, covering representative POSTs, every `$except`, policy-aware origin cases and a valid success control.
5. Run identical applicable checks on B/P/C, then produce C↔P and C↔B comparisons. Level 0 includes manifest/lock and real-platform validation, isolated boot, route-list diff, the entire suite with identities/statuses, and a main-page HTTP smoke for every audited role on a throwaway synthetic DB. Use `python3 -I <path-to-compare_junit.py> left.xml right.xml` for JUnit identity/status comparison; preserve original CLI exits, warnings and logs. Confirm positive controls: all-404 routes, all-419 CSRF, blank PDFs and unsent mail cannot establish parity.
6. Enforce the hard stops and approval scope in [templates](../laravel-upgrade/references/templates.md): unapproved decisions, security regressions, real-service access, exposed secrets, destructive schema work, or lost B evidence stop execution. Never treat an owner approval as permission to accept a security regression. Keep behavior parity, all-green suite, security status and deployment readiness separate. A reproduced old failure can establish parity only with recorded approval; it remains a failing test.
7. Close a hop as **VERIFIED IN <environment>** only when Level 0, applicable Level 1 and risk-required Level 2 are complete with no unresolved regression. A named pre-approved Level 1/2 exception is **PARTIAL**, not VERIFIED; any missing Level 0 is **BLOCKED**. For the final candidate, run the terminal C↔B comparison in addition to the hop's C↔P check, then provide the final summary. Report exact coverage, failures/skips/warnings/deprecations, approved exceptions, unknowns and evidence paths. No commit, push, PR or deploy is implied; the separate approved range command grants only the local per-hop commits defined in the templates.
